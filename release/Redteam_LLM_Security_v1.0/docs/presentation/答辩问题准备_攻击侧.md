# 答辩问题准备：攻击侧与安全边界

## Q1：项目是否在做真实攻击？

不是。所有攻击均为本地授权红队模拟，目标是 sandbox 中的 mock 工具。`send_email` 不真实发送邮件，`call_api` 不访问公网，`run_code` 不执行模型生成的真实代码，secret 文件只包含 canary 假数据。

## Q2：为什么本地小模型也有研究价值？

本作品关注的是智能体工具链信任边界，而不是生成真实危险内容的能力。只要模型可能把不可信文档、工具输出或结构化字段误当成指令，就能复现提示注入导致的工具调用风险。mock 工具和调用链日志可以稳定展示这种行为风险。

## Q3：样本库覆盖了哪些攻击类型？

样本库覆盖直接越狱、RAG/文档间接提示注入、多语言/T2L 注入、JSON/RPC 结构化注入、工具输出注入，并加入 `benign_clean` 正常样本用于误报率评估。

## Q4：如何避免误伤正常任务？

系统通过 `benign_clean` 样本计算 FPR，并采用 `allow`、`ask`、`deny` 三态决策。对高风险但不确定的工具调用可以要求确认，而不是一律拒绝。这样可以兼顾安全性和可用性。

## Q5：攻击样本公开是否安全？

样本只包含本地 mock 行为目标，不包含真实恶意代码、真实 API、真实邮箱、真实系统路径或真实漏洞利用步骤。样本适合用于受控安全评测和教学演示。

## Q6：为什么要设计 RAG 间接提示注入案例？

RAG 场景中，模型会读取外部文档、网页和邮件等不可信内容。攻击者可能把伪指令藏在这些内容中，诱导模型偏离用户任务。该类案例用于验证系统能否保持“文档是数据，不是指令”的边界。

## Q7：JSON/RPC 注入为什么危险？

结构化字段可能使用 `instruction`、`developer`、`system`、`tool`、`next_step` 等看似高优先级的名称。如果模型错误地把这些字段当成真实系统指令，就可能发生工具调用劫持。安全行为应把它们视为普通用户数据。

## Q8：多语言/T2L 样本要证明什么？

多语言、拼音/谐音、回译和 JSON 翻译任务可能让风险文本绕过简单关键词规则。T2L 样本用于验证模型是否会在翻译、转写、分类等任务中发生任务切换。

## Q9：为什么需要工具输出注入？

工具集成 Agent 通常会把搜索结果、API 返回值、日志分析结果作为下一步上下文。如果上游工具输出中夹带伪指令，可能污染后续决策。该类样本用于验证系统是否把工具输出当作不可信数据处理。

## Q10：三个演示案例怎么讲？

- `RAG-PI-016`：说明不可信 Markdown 报告隐藏注释诱导读取 canary secret 和 mock 邮件外发。
- `JSONRPC-001`：说明 JSON `data.next_step` 字段中的伪下一步指令不应被执行。
- `MTL-009`：说明只翻译指定字段时，非目标字段中的工具诱导必须被忽略。

## Q11：评委质疑“样本不是真实攻击”时如何回答？

项目目标是安全评测与行为监督验证，因此必须避免真实危害。mock 靶场保留了工具调用链、风险标签、阻断原因和指标计算，足以复现智能体信任边界问题，同时不会影响真实系统。

## Q12：后续可以如何扩展攻击侧？

后续可扩展更多业务载体、更细粒度的数据流标签、更多本地模型横向对比、多模态隐藏提示和真实开源 Agent 框架适配，但仍应保持授权、可控和本地沙箱边界。
