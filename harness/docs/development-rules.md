# 开发规则

## 通用规则

- 修改前先阅读。
- 保持改动小而明确。
- 除非任务明确要求改变，否则保留现有架构和风格。
- 优先复用现有项目工具、模式和抽象。
- 避免无关的格式改动。
- 行为变化时同步更新测试和文档。
- 在 `harness/docs/decision-log.md` 中记录架构决策。

## 任务范围规则

每个任务必须定义：

- 目标
- 允许修改的文件或目录
- 禁止修改的文件或目录
- 验收标准
- 验证命令

如果范围不清楚，智能体可以检查代码库，但在范围澄清前不得实施高风险改动。

## 可读命名与路径长度

- 新文件名（含扩展名）最多80个UTF-16单位；单级目录最多64；仓库相对路径最多180；本机绝对路径最多240，给复制目的地保留余量。以上是项目预算，不是Windows极限。
- 保留完整、可理解的含义；先消除研究名、条件名在目录和文件名里的重复，再减少层级。使用`records.jsonl`（逐条结果）、`metrics.csv`（汇总指标）等完整单词；不用随意截词、难懂首字母或无含义编号替代名称。
- 模型、参数、时间和完整运行身份写入记录内容，不反复拼入每一级目录及文件名；不同条件须有唯一且可读的目录或文件名。
- 创建或迁移前运行`python -X utf8 -B harness/scripts/check_paths.py 新路径...`；退出非零先改命名，不以系统长路径开关代替修复。无参数检查暂存新增及改名。
- 定向测试可在隔离的生成目录故意构造边界路径，用于验证拒绝或Git兼容性；这类测试夹具不能成为正式产物的命名范例。
- 原版参考文献在`docs/文档资料/`下可保留完整题名，已有暂存中的历史`文档资料/`同样保留题名；两者仍遵守目录及完整路径预算。已有冻结输入、原始证据内路径、第三方内部结构和无关暂存不自动改写；无法安全迁移的历史例外记录原因，不宣称已经消除。

## 代码规则

- 实现能满足任务的最小设计。
- 没有记录理由时不得引入新依赖。
- 不为一次性行为增加宽泛抽象。
- 除非任务要求改变，否则保持公开接口稳定。
- 错误信息必须明确且可操作。
- 注释应简洁、有用，并优先使用中文；技术标识和上游原文可保留英文。

## 测试规则

- 为变化的行为新增或更新测试。
- 使用最接近的既有测试模式。
- 开发过程中运行针对性检查。
- 条件允许时，在声称完成前运行完整验证流程。
- 若某项检查不可用，必须记录原因。
- 必需检查失败时，不得将功能标记为 `verified`。

## 文档规则

出现以下情况时更新文档：

- 用户可见行为变化。
- 配置、命令或环境假设变化。
- 架构或模块边界变化。
- 某项决策形成未来维护义务。

## 安全规则

- 不读取或输出密钥。
- 不提交凭据。
- 未经明确指示和复核，不得削弱认证、授权或权限检查。
- 生产部署和数据库修改必须视为需要确认的动作。
- 将日志写入仓库文件前先进行脱敏。

## Git 与仓库规则

- 不破坏用户工作。
- 未经明确要求，不运行破坏性历史命令。
- 不回退无关改动。
- 除非生成物本来就是源资产，否则不将其纳入提交。
- 在任务历史中记录有意义的改动。

## 功能状态规则

使用 `harness/features/feature_list.json` 作为交付台账。

- `planned`：已知但尚未开始。
- `in_progress`：实现或验证进行中。
- `verified`：实现、验收标准和必需检查均已通过。
- `blocked`：没有决策、依赖或外部修复就无法继续。

不得把 `verified` 当作“已经实现”的同义词。
