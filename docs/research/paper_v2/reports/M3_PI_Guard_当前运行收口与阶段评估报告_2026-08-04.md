### 3.2 技术门失败的两类原因

shard 0 有一个真实的冻结门禁失败：

- 冻结规则要求每个 recovery 分片 diagnostic 不超过 `floor(N × 1%)`；
- shard 0 的上限为 6，实际为 10；
- 因此 `diagnostic_fraction_within_frozen_bound=false`，即使修正下面的代码缺陷，shard 0 仍会在原分片门禁下失败。

shard 1 暴露出一个独立的工程缺陷：

- shard 1 diagnostic 为 4，上限为 6，诊断比例门本应通过；
- 其余正向技术检查也均通过；
- 但 review 将 `source_terminal_records_retried=false` 直接放入 `checks`，随后使用 `all(checks.values())`；
- 由于“没有重试”被表示为 false，`all(...)` 必然返回 false，使两个 recovery 分片无条件无法通过技术门。

正确的布尔检查应表达为 `no_source_terminal_records_retried=true`，或将检查值设为 `source_terminal_records_retried is False`。历史 review 工件不能原地改写，后续应新建版本化 review/reconciliation；本轮没有为绕过门禁而修改它。

## 4. Gemini Public segment 1 失败分析

### 4.1 实际发生的调用链

Gemini segment 1 获得独立 admission，限制为 2 个 canary records、最多 16 次请求、并发 1、自动重试 0、免费层、paid ceiling USD 0。运行只触碰第一个 work item，随后 fail closed。

保留的元数据链如下：

1. 调用前生成本地 client request ID；
2. 调用前冻结 canonical payload SHA-256；
3. started 事件 append、flush、fsync；
4. Google 官方 OpenAI-compatible endpoint 返回 HTTP 200；
5. 返回模型精确为 `gemini-3.6-flash`；
6. 官方 response ID 存在；
7. provider request ID 缺失；
8. completed trace 已追加，started/completed 链闭合；
9. 历史 record contract 将缺少 provider request ID 的 receipt 降为 diagnostic；
10. Gemini trace attachment 发现该 diagnostic 仍携带 response claim，按 fail-closed 规则抛出异常；
11. 没有生成 experiment record，work-item attempt 保持 open，segment 永久封存。

异常类型为：

`GeminiTraceAttachingRuntimeV1Error: incomplete Gemini trace cannot retain a response claim`

### 4.2 为什么不是 429

本次 provider call 的 HTTP 状态为 200，且存在官方 response ID、精确模型身份和 usage。wrapper 失败发生在响应后的证据附着阶段，不是传输限流阶段。Google AI Studio 的免费层配额仍然需要按项目日账本管理，但不能把本次失败归因于免费额度。

### 4.3 证据契约冲突

项目研究计划已经把“调用前本地 request ID + payload hash + 官方 response ID + 精确模型身份 + append-only 日志”定义为可接受完整链。然而历史 `experiment_record_v1` 语义仍要求正式记录同时拥有 provider request ID 与 response ID。

因此当前存在明确的规范不一致：

- provider trace 协议允许 `precommitted_local_plus_provider_response`；
- Gemini trace 已满足该模式；
- 通用 experiment record 的 formal 语义仍不允许 provider request ID 为空；
- Gemini 运行时适配器无法在不违反旧契约的情况下提升该记录。

这应通过前瞻性的 experiment-record/attestation 新版本解决，不能追溯升级本次响应，也不能伪造 provider request ID。
