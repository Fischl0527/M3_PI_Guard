## 2. 完成的实现

### 2.1 v7 后置非授权门禁

新增 `experiment_closeout_harness_gate_v5.py` 和对应冻结工件。门禁把以下证据绑定
到一个可重放的 SHA-256 链：

- Fresh Harness v7 的 launch、running、stdout、stderr、receipt、helper 与 launcher；
- 历史 medium controller-v7 的不可恢复失败审计；
- Gemini Public-v5 segment 0 的技术审查与 wrapper receipt；
- Adaptive 执行顺序门、Pro-50 v2 candidate 和 admission；
- 新 Adaptive wrapper、门禁源码及其定向测试。

门禁状态为 `fresh_v7_full_harness_execution_prerequisite_satisfied`，但明确保持
`provider_execution_authorized_by_gate=false` 和
`result_access_authorized_by_gate=false`。它证明前置证据一致，不自行授权 API 或
结果访问。

### 2.2 Adaptive Pro-50 单用途包装器

新增 `run_adaptive_formal_pro_v2_guarded_v3.ps1`。包装器只接受 `pro_50`，只允许
使用新的单用途运行目录，并依次执行：

1. v5 Harness gate；
2. Adaptive order gate；
3. candidate 复核；
4. admission 复核；
5. exact-stage execute；
6. outcome-blind technical review。

包装器固定自动重试为 0、provider tools 为 false、external effects 为 false，
并将每一步 stdout/stderr、退出码和 SHA-256 写入终态 receipt。若运行根已存在、
输出根被触碰、身份/任务数漂移、结果准入被打开或日志出现 secret 格式，则拒绝
继续。当前 wrapper 只完成资格化，未被执行。

### 2.3 Harness 集成

`harness/scripts/verify.ps1` 已登记 v5 门禁源码/工件、v3 Adaptive wrapper 和新的
Fresh Harness v8 launcher，并在 paper-v2 closeout 前瞻证据阶段重放 v5 门禁。
新增 v8 单用途 launcher，沿用 receipt helper v3；它在子进程中清空全部 API 环境
变量，禁止 provider/network authority，不自动重启。

## 5. 过程中发现并解决的问题

第一次门禁构建在 AgentDojo Git ownership 检查处失败；第二次把 AgentDojo 改为
process-scoped `safe.directory` 后，又在 VIGIL checkout 遇到相同问题。最终对 15
个明确的外部固定 checkout 只在当前进程环境中加入精确 safe-directory 项，并在
上下文结束后恢复原环境；没有写 global/system/repository Git 配置。

第三次门禁构建因受限沙箱无法读取已存在的 Python 3.13 用户 site-packages，表现为
`openai` 缺失。只读确认表明 `openai 2.33.0` 已安装；在获准的非沙箱只读环境中
复现后门禁成功。没有安装、升级或改写依赖。

Ruff 第一次在沙箱中因可执行文件访问受限而无法启动；在同一现有可执行文件的
非沙箱只读检查中通过。以上失败都发生在离线资格化阶段，没有创建 provider
请求、预算预约或正式结果。
