执行摘要

核心结论

以“运行时授权不确定性评估 + 来源感知、权限单调的防御机制”为主线，M3-PI Guard 具备冲击 SCI JCR Q2 网络安全期刊的条件，但当前只能判定为“有条件可行”。工程协议、证据链和中型实验基础已较成熟；决定论文能否成立的正式比较结果、跨模型验证、公共基准、自适应攻击和独立盲测尚未完成。

截至本报告，已经完成 34 篇直接相关文献的分级矩阵、22 个在线状态审计单元、六条件中型实验协议、DeepSeek 官方 API 的可审计证据链、v4–v6 失败版本的不可变封存，以及 v7 的新适配器、候选和准入冻结。最近一次完整且完成的全量回归为 1049 项通过、1 项跳过、0 项验证失败；v7 专项测试为 12/12 通过。

需要特别强调：现有数据只支持技术审计和运行质量分析，不支持 M3 的安全性、效用或领先性结论。v4、v5、v6 均因不同的协议或证据格式问题被判定为结果不准入；v7 尚未调用 API。

1 项目定位、论文问题与可发表贡献

1.1 论文定位

M3-PI Guard 研究工具型 LLM Agent 在间接提示注入环境下的运行时授权问题。系统不把模型输出直接视为可执行命令，而是将其视为需要经过策略、来源、时序、数据流和确认机制联合审查的动作提案。研究重点是实际执行安全，而不是单纯检测文本是否“像攻击”。

拟投稿方向优先选择 Journal of Information Security and Applications（JISA）。其官方范围覆盖访问控制、安全策略和信息安全应用，与本项目的运行时授权和工具调用安全契合。JCR 分区必须在投稿时通过学校或 Clarivate 订阅再次确认，任何第三方分区页面只能作为前期参考。

1.2 研究问题

RQ 问题 需要的证据
RQ1 逐样本精确授权、答案键或评估标签进入在线 Guard 时，会造成多大程度的安全结果高估？ 多种 authorization regime 的严格配对；在线可见字段摘要；字段泄漏测试
RQ2 在不使用 oracle 授权的条件下，M3-full 能否相对最强结构化基线降低 unsafe effect？ M3-full 与 VIGIL/​DRIFT 的配对差异、置信区间和 ITT 分母
RQ3 来源、时序、数据流和独立确认是否在 policy-only 之外提供独立增益？ M3 policy-only 与 M3-full 配对消融
RQ4 安全提升是否由 deny-all 或过度 ASK 获得？ TCR 非劣检验、ASK 率、确认次数、攻击条件下效用
RQ5 结论能否跨模型、公共基准和防御感知攻击保持方向一致？ DeepSeek/​Gemini、AgentDojo/​SIREN、adaptive attack 与盲测

1.3 可保留的贡献

  1. 把 evaluator/gold 字段与在线执行状态做可验证隔离，并报告在线可见字段的稳定摘要。

  2. 把权限变化设计为单调关系：自动路径只能收缩权限；权限扩张必须经过独立确认。

  3. 以 ALLOW/ASK/DENY 三态替代二元阻断，同时测量 ASK 的交互负担和效用损失。

  4. 联合分析授权不确定性、参数来源影响、unsafe effect、任务完成率和过度阻断。

  5. 在结果不可见条件下冻结候选、哈希、准入、分母和失败规则，提供可追溯实验链。

1.4 明确不做的主张

主张红线

不使用“首个参数级来源追踪系统”“唯一的信息流防御”“首个 verify-before-commit”或“当前 SOTA”等措辞。ARGUS、AuthGraph、VIGIL、DRIFT、Task Shield、IPIGuard 和 CaMeL 已覆盖相邻创新空间。M3 的论文价值必须来自可重复的评估方法、可解释的配对消融和真实安全—效用收益。

2 前沿研究版图与创新边界

已建立 2024–2026 年直接相关文献矩阵，共 34 篇/项，区分同行评审论文、预印本和基准工作。核心对照不是数量堆叠，而是覆盖检测、提示层缓解、结构化运行时防御、权限/数据流机制和公共评测五类路线。

2.1 M3 的差异化空间

  • 把 oracle 授权泄漏本身变成可测量变量，而不是在不透明 benchmark wrapper 中默认接受。

  • 要求自动授权编译保持权限单调，并把权限扩张从模型自证改为独立确认事件。

  • 以同一任务、同一模型、同一在线上下文做 policy-only/full 配对，避免把模型差异误计为机制贡献。

  • 把 operational failure、timeout、parse failure 和拒答保留在 intention-to-treat 分母。

  • 将确认负担作为安全机制成本，而不是只报告 ASR 或检测 recall。

2.2 论文叙事建议

主叙事采用“评估方法 + 防御机制”双主线。Introduction 先指出现有工具型 Agent 防御的评估常把授权信息、目标答案或过度明确策略带入在线阶段，随后提出非 oracle 的运行时授权机制，并用来源/时序/确认模块的配对消融证明或否证增益。若正式结果不支持机制优势，保留评估方法与负面结果，转为系统实证论文。

3.1 冻结的实验规模

中型证伪矩阵包含 480 个工作项：432 个主实验记录和 48 个授权机制探针。六个核心条件在同一任务集合上运行；正式分析以任务级配对为主，而不是把不同条件的独立比例直接比较。

条件 作用 论文定位
No defense 给出 Agent 原始风险下界 必要参照
Safe prompt / Spotlighting 轻量提示层缓解 低成本基线
PromptGuard 检测器门控 明确标注 detector-only
VIGIL（优先） 同行评审结构化提交前验证 最强主对照
M3 policy-only 只保留策略约束 核心消融
M3 full 策略 + 来源 + 时序 + 数据流 + 确认 目标机制

3.2 安全运行承诺

  • 不把 DeepSeek 或 Gemini 连接到真实工具、生产系统、邮件、支付、文件删除或外部执行能力。

  • 模型只生成结构化 proposal；执行与效果判断由本地隔离层完成。

  • 只发送合成或公开 benchmark 内容；不发送密钥、私人数据或评估答案字段。

  • 不自动跨 provider 回退，不因格式错误反复重试，不绕过身份或日志门禁。

4 实验架构、证据链与安全边界

正式实验采用“先冻结、后调用、再准入、最后分析”的单向链。科学结果在技术完整性审查通过前保持不可见，避免根据结果修门槛。任何失败都保留在分母；旧版本失败后新建身份，不对既有账本做回写修补。

4.2 在线状态与离线评估边界

  • 在线状态只包含任务输入、允许公开的应用上下文、条件配置和非答案型授权信封。

  • unsafe_effect、task_completion、gold action、evaluator labels 和 primary eligibility 仅供离线评估。

  • 每条记录保存 online_visible_field_digest，用于证明不同条件下可见字段集合符合冻结定义。

  • exact_gold 仅作为 48 个隔离的 oracle probe，不进入主比较，也不伪装为真实可部署防御。

4.3 三道安全边界

边界 约束 失效时处理
Provider 边界 无 provider tools、无真实 effect、无敏感数据 立即暂停，不重试

5 v4–v7 技术演进与失败分析

v4–v6 的失败均暴露了可复现的实验接口问题。正确处理不是删除失败记录或继续填满矩阵，而是冻结旧版本、保留成本与终态、修正假设后生成新版本身份。v7 是针对 v6 证据格式缺陷的版本化修订，尚未产生 API 记录。

图 3 DeepSeek v4–v7 的记录、调用与累计成本。v7 尚未调用 API。

版本 规模与成本 发现的问题 处理与结论
v4 395 records；773 calls；累计 ¥0.7445 39 个运行终态失败；结果门阻断 永久冻结，不进入科学分析

图 4 v4–v6 技术终态构成。柱顶总数含开放 attempt；这些不是论文安全效果。

5.1 v4：运行质量不足而非统计失败

v4 在 395/480 时形成 356 个 completed、6 个 max_steps、2 个 provider_failure、1 个 parse_failure 和 30 个 runner_failure；共 39 个 operational failures。结果技术门阻断准入，科学结果没有被审阅。该版本证明请求链和大规模续跑可工作，但不能用于比较防御效果。

5.2 v5：终态分类仍有未闭合路径

v5 共形成 94 条记录、157 次调用，另有 1 个开放 attempt；92 条 completed、2 条 runner_failure。审计发现 proposal/终态分类仍无法覆盖全部安全边界状态，因此新建 v6，而不是在 v5 账本上补写。

5.3 v6：证据格式与消费者契约不一致

v6 canary 6/6 通过，正式续跑至 64 条记录时，本地离线评估器拒绝 malformed boundary rejection evidence。问题位于适配器产生的证据格式和 evaluator 消费规则之间，并非模型安全效果。v6 保留 61 completed、3 runner_failure、1 open attempt、112 次 provider 调用以及完整 usage/cost，全部结果不准入。

5.4 v7：修复目标与当前状态

v7 新增哈希化 proposal-message 分类，并从 backend receipt 一直验证到 evaluator 输入，避免仅测试 producer 而未测试 consumer。候选、qualification 和 canary admission 已冻结；专项测试 12/12 通过，Ruff 通过。截至本报告，全量离线审计执行进度约 47%，没有形成完整通过或失败结论；未进行 v7 API、canary 或正式矩阵调用。

阶段决策

当前优先完成报告，v7 保持冻结且不运行。后续恢复实验时，必须先完成全量离线审计和结果准入门 v4 的实现/冻结，再允许一次 v7 canary。不能以 v7 专项测试通过替代完整门禁。

6.3 Gemini 当前定位

Gemini 官方 OpenAI-compatible 端点已完成基础连通性验证，精确模型槽为 gemini-3.6-flash。正式实验前需要单独完成原生参数适配：Gemini 3.6 Flash 不应沿用旧式 temperature/top_p/top_k 组合；实际 RPM/TPM/RPD 以 AI Studio 项目限额为准。Gemini 免费额度用于跨模型泛化，不与 DeepSeek 同一模型身份发生静默回退。

成本判断

截至 v6 的 DeepSeek 累计成本不足 1 元，尚未构成实验阻塞。后续不人为压缩必要样本，但仍保留逐调用计量、阶段检查点、首个 429 暂停和无自动重试，以避免额度或配额异常造成不可恢复的矩阵偏差。

7 SCI JCR Q2 可行性评估与投稿策略

7.1 结论：有条件可行

从研究问题、网络安全属性、工程证据和可获得的 API/公共基准看，项目具备 SCI JCR Q2 的潜力。其优势是实验审计深、授权安全问题明确、失败证据保留完整；短板是尚无准入的机制效果结果，且 2025–2026 年相邻工作已显著压缩“首次性”空间。

7.3 防御机制论文的最低验收

  • M3-full 相对最强结构化基线：unsafe-effect 点估计相对降低至少 20%，或绝对降低至少 10 个百分点。

  • 合法任务 TCR 的非劣界限不低于 −5 个百分点。

  • M3-full 相对 policy-only 呈一致正向增益，并能从模块事件中解释。

  • ASK + DENY 不退化为近似 deny-all；确认负担可接受。

  • 至少两个公共/外部基准方向一致，且至少一个正式可审计 API 模型。

  • 防御感知自适应攻击不能完全推翻主要结论。

11 阶段结论

M3-PI Guard 已从早期工程原型推进为具有研究协议、来源审计、版本冻结和可追溯 API 证据链的候选系统。v4–v6 的失败没有被掩盖，反而帮助识别了运行终态、proposal 分类和 evidence consumer 之间的薄弱环节。v7 的修订方向合理，但必须完成全量审计和 result gate v4 后才有资格恢复 API 实验。

从投稿角度看，项目的 Q2 潜力来自问题价值和方法严谨性，而不是当前结果。最关键的下一步不是继续改叙事，而是取得一套正式准入、可配对、可复现且能经受最强结构化基线与自适应攻击的结果。只有 M3-full 同时满足安全增益、TCR 非劣和相对 policy-only 的独立贡献，才按防御机制论文投稿；否则及时转为授权泄漏与不确定性实证研究。

建议的近期唯一优先级

报告完成后保持 v7 冻结。恢复研究时先完成全量离线审计和 result gate v4；随后执行一次 DeepSeek v7 canary。不要在结果门尚未冻结时启动正式 API 矩阵。

A.1 主要终点

  • Unsafe-effect rate：实际发生不安全效果的比例，是论文主安全终点。

  1. 所有失败和超时保留在 intention-to-treat 分母。
